## Context

项目目标是为私网环境准备可安装的 Python 三方依赖包。现有实现已经具备 `uv -> pip` 的基础链路，但在老旧库场景存在三个核心问题：  
1) 缺少“不可满足 vs 工具异常”的明确分类，导致回退策略不够精准。  
2) 老旧 sdist 获取依赖本机构建元数据流程，容易被当前解释器/构建链影响。  
3) 缺少“离线可安装性预演”，风险往往在私网安装阶段才暴露。  

因此需要把解析、采集、验证升级为完整闭环，并保持默认路径兼容。

## Goals / Non-Goals

**Goals:**
- 保持 `uv` 为首选解析器，同时提供可解释的回退分类。
- 让用户在下载结束前即可知道依赖覆盖状态和失败原因。
- 提升老旧包采集成功率，减少对执行机 Python 版本的耦合。
- 在公网端提前验证离线包可安装性，提升私网成功率。
- CLI/GUI 语义一致，支持基础模式与高级模式并存。

**Non-Goals:**
- 不承诺“100% 覆盖全部历史三方库”。
- 不在本次变更中引入完整私有仓库镜像服务（如 devpi/Artifactory）。
- 不在本次变更中自动编译所有源码包（仍以采集与引导为主）。

## Decisions

### 决策 1：保留 uv-first，但引入失败分类器

- 方案：
  - `uv` 解析成功：进入标准下载阶段。
  - `uv` 失败且属于“执行异常/环境异常”：回退 `pip` 解析路径。
  - `uv` 失败且属于“目标不满足（无匹配 ABI/版本）”：直接标记 `unresolved`，不做无效重试。
- 理由：避免把天然不可满足问题误判成可自动修复，提高结果可信度。
- 备选：所有 uv 失败都直接回退 pip。  
  - 放弃原因：会放大噪音重试，用户仍无法区分真实不可满足原因。

### 决策 2：构建“老旧包弹性采集器”并弱化本机构建依赖

- 方案：对 `source-required` 包优先走“索引元数据直连下载”路径（sdist 文件抓取与哈希校验），仅在必要时使用 pip 的 sdist 路径。
- 理由：减少 legacy 包在本地触发 PEP517/构建元数据失败的概率（如 `distutils` 兼容问题）。
- 备选：继续完全依赖 `pip download` 的回退。  
  - 放弃原因：对老旧库命中率不足且失败原因受本机环境扰动大。

### 决策 3：增加覆盖报告与可安装性预演

- 方案：新增三类报告：
  - `dependency-tree.json`：结构化依赖树。
  - `coverage-report.md`：按包输出覆盖状态、原因、建议动作。
  - `installability-report.md`：联网端模拟私网安装结果（通过/失败）。
- 理由：将风险前置，减少私网环境试错成本。
- 备选：仅输出下载日志。  
  - 放弃原因：日志难以快速审计和自动化消费。

### 决策 4：双模式交互（基础模式兼容 + 高级模式闭环）

- 方案：
  - 基础模式：保持当前体验，尽量少参数。
  - 高级模式：增加“覆盖报告确认 -> 执行下载 -> 可安装性校验”流程。
- 理由：兼顾可用性与学习成本，避免强制改变现有用户习惯。

### 决策 5：建立统一状态模型并作为跨层契约

- 方案：定义三层状态并统一输出到 CLI、GUI、报告文件。
  - 任务级状态（JobState）：
    - `created`：任务已创建，尚未开始
    - `resolving_uv`：uv 解析中
    - `resolving_pip_fallback`：回退到 pip 解析中
    - `planning_ready`：依赖树与覆盖报告已生成，等待确认
    - `downloading`：下载中
    - `verifying_installability`：离线可安装性预演中
    - `completed`：成功完成
    - `completed_with_risks`：完成但存在 `source-required/unresolved`
    - `failed`：失败并终止
  - 依赖级状态（DependencyState）：
    - `pending`：待处理
    - `resolved`：已解析
    - `wheel_ready`：目标环境 wheel 可直接使用
    - `source_required`：需源码处理
    - `manual_required`：需人工选择替代版本/构建策略
    - `unresolved`：当前目标下不可满足
  - 产物级状态（ArtifactState）：
    - `missing`：未生成
    - `generated`：已生成
    - `validated`：已校验通过
    - `invalid`：生成但校验失败
- 理由：解决“状态分散在日志文本里”的问题，便于自动化检查和 GUI 呈现。
- 备选：继续使用纯文本日志描述状态。  
  - 放弃原因：难以维护一致性，且不利于测试与审计。

### 决策 6：将旧变更能力并入主变更并标记来源

- 方案：把 `dependency-tree-review-gate` 的需求并入主变更 specs/tasks，并在旧变更内添加“已并入主变更”标记。
- 理由：主线唯一，避免双变更并行实现导致冲突。
- 备选：两个变更并行推进。  
  - 放弃原因：任务重复、文件冲突概率高、验收边界不清晰。

## Risks / Trade-offs

- [风险] 额外报告与校验增加任务时长。  
  → 缓解：默认关闭高级校验，按需开启。
- [风险] 直连下载路径在部分索引镜像上元数据不一致。  
  → 缓解：保留 pip 路径作为兜底，并在报告中记录源与校验结果。
- [风险] 部分 C 扩展即使成功下载仍可能私网编译失败。  
  → 缓解：报告明确标注“需目标环境工具链”，并给出最小构建前置清单。
- [风险] 失败分类规则初版可能不完美。  
  → 缓解：规则配置化并逐步补充样本测试。
- [风险] 状态模型过细导致实现复杂度提高。  
  → 缓解：首版固定最小状态集合，超出部分先映射到 `manual_required` 与 `completed_with_risks`。
- [风险] 旧变更与新变更并存期间团队误用旧任务清单。  
  → 缓解：在旧变更文档显式写入“superseded by offline-dependency-bundle-completeness”。

## Migration Plan

1. 实现失败分类器与覆盖报告模型，不改默认 CLI 行为。  
2. 引入老旧包弹性采集路径，并增加对应测试样本。  
3. 增加离线可安装性预演命令与报告。  
4. 在 CLI/GUI 接入高级模式与确认流程。  
5. 接入统一状态模型并补齐状态迁移测试。  
6. 将旧变更标记为并入主变更，统一维护主变更任务。  
7. 更新 README/QUICKSTART/TECHNICAL_OVERVIEW 与 evidence 模板。

## Open Questions

- 直连下载路径是否优先支持 `https://pypi.org/simple`，还是同时支持主流镜像差异协议？
- 可安装性预演是默认在“当前解释器”执行，还是允许指定独立解释器路径？
- 状态模型是否需要对外提供机器可读 API（例如 JSON schema 版本号）？
