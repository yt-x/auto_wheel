## Context

当前 `auto-wheel` 的主流程是“解析后立即下载”，高级用户在下载前无法确认依赖树完整性与目标平台覆盖率。  
在跨平台场景下，`resolver` 的平台映射粒度偏粗、`downloader` 的源码回退会移除目标约束，存在“下载结果混入主机平台产物”的风险。  
本变更需要同时覆盖 CLI 与 GUI，且必须保持默认行为兼容，避免影响现有自动化脚本和使用习惯。

## Goals / Non-Goals

**Goals:**
- 增加“依赖树预览 + 覆盖报告 + 人工确认”能力，让用户在下载前可审计依赖结果。
- 为高级用户提供“确认后再下载”的执行闸口，形成可追溯流程。
- 提升平台映射与覆盖判定精度，区分平台与架构，降低误判。
- 收敛源码回退边界，避免目标平台下载任务被主机平台 wheel 污染。
- 在 CLI 与 GUI 两个入口保持一致语义和一致提示。

**Non-Goals:**
- 不引入新的依赖解析引擎（仍以 `uv + pip` 组合为主）。
- 不在本变更中新增第三方图形可视化库（先采用 JSON + ASCII + Markdown 报告）。
- 不改变默认“直接下载”路径；新闸口作为高级模式能力。

## Decisions

### 决策 1：采用“两阶段执行模型”，默认兼容，按需启用闸口

- 方案：新增“解析预览阶段（plan）”与“下载执行阶段（apply）”。
  - `plan`：只解析并输出 `dependency-tree.json`、`dependency-tree.txt`、`coverage-report.md`。
  - `apply`：在 `--approve-tree`（或 GUI 勾选确认）后执行下载。
- 原因：满足“先确认依赖树再执行”的高级需求，同时保持现有默认路径不破坏。
- 备选方案：强制所有用户先确认再下载。  
  - 放弃原因：会破坏现有 CLI 自动化场景，回归风险高。

### 决策 2：将平台映射从“类别映射”升级为“目标三元组/细粒度平台映射”

- 方案：新增统一的目标平台标准化函数，优先映射到 `uv --python-platform` 的具体值（例如 `x86_64-manylinux2014`、`aarch64-manylinux2014`、`x86_64-pc-windows-msvc`）。
- 原因：减少跨架构误解析，提升覆盖报告可信度。
- 备选方案：继续使用 `linux/windows/macos` 粗粒度映射。  
  - 放弃原因：不能准确表达架构差异，会持续产生“覆盖不全”误报/漏报。

### 决策 3：源码回退阶段仅补拉源码包，禁止下载主机 wheel

- 方案：回退时保留目标约束语义，并显式采用“只接收 sdist”策略；若目标约束与 pip 限制冲突，则输出不可自动补齐状态并写入覆盖报告。
- 原因：保证交付物语义清晰，避免“下载成功但目标不可安装”的隐性错误。
- 备选方案：维持当前“移除目标约束再重试”。  
  - 放弃原因：结果不可审计，存在污染风险。

### 决策 4：报告输出由核心层生成，CLI/GUI 仅做展示与确认

- 方案：在核心模块新增报告模型与文件输出；CLI 负责参数和文案，GUI 负责展示与确认交互。
- 原因：避免 CLI/GUI 各自实现解析逻辑，保持 DRY。

## Risks / Trade-offs

- [风险] 解析预览增加一次子进程调用，整体耗时上升。  
  → 缓解：默认流程不强制启用；高级模式开启时明确提示“预览阶段会增加耗时”。
- [风险] 部分包索引元数据不完整，导致覆盖报告存在“未知状态”。  
  → 缓解：报告中增加 `unknown` 分类，并提示用户使用 `--dry-run` 二次验证。
- [风险] pip/uv 版本差异导致输出格式变化，影响解析稳定性。  
  → 缓解：优先使用结构化输出（可用时 JSON）；为文本解析保留回退并补测试样本。
- [风险] GUI 增加确认步骤后交互复杂度提高。  
  → 缓解：默认隐藏高级面板，仅在勾选“高级模式”后显示确认流程。

## Migration Plan

1. 新增预览与报告能力（不接入默认主流程），先补充单元测试。
2. 在 CLI 引入 `--plan-only` / `--approve-tree` 参数，并保持旧参数兼容。
3. 在 GUI 增加“依赖树预览与确认”面板，默认关闭高级模式。
4. 更新 README 与技术文档，加入新流程示例和边界说明。
5. 灰度验证：以典型跨平台依赖集合（含无 wheel 包）回归测试。
